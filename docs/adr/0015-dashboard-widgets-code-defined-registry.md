# Dashboard widgets are code-defined via a registry, with a sparse per-user JSON override

The dashboard is composed of **Widget definitions declared in code** (a `registry.ts` that exports `WidgetDefinition[]`), not rows in a database-backed widget builder. The registry declares the default instances and their order; a user's actual layout is a sparse JSON override (a list of instances keyed by a stable instance key) merged over those defaults, stored per user in `DashboardLayout`.

Widget identity is therefore a code string (e.g. `trend-revenue`) with no foreign key in the database. This is deliberate. The alternative — a database-driven widget model where users compose arbitrary persisted widget rows, or a materialized per-user layout at account creation — was rejected because it duplicates the visual page builder (Puck) for a much smaller surface and makes the default layout hard to evolve. With a registry plus a sparse merge, adding a widget is one module and one registry entry; removing one drops it from every user's effective layout with no migration; and a role's default emerges from the permissions each definition declares, so no per-role layout storage is needed in v1.

A definition may also declare a **config schema**, resolved against the user's context (for the Trend, the metrics the user may read). The chosen config is stored per instance in the same sparse per-user document, so a widget becomes configurable — and a new configurable widget appears — with no model change. Multiple instances of one definition are allowed, so two Trend widgets can chart different metrics.

The cost is that the database cannot enforce the set of valid widget ids, and the merge function (permission filtering, key overlay, append-new, drop-unknown) is the single place that defines what a user actually sees. That function is pure and tested precisely because it carries this responsibility. If a future requirement demands arbitrary admin-authored widget types or per-role layouts in the database, a per-role default can be inserted as an additional layer above the registry defaults without changing the storage shape.
