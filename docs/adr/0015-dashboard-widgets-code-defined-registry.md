# Dashboard widgets are code-defined via a registry, with a per-user JSON layout

**Status**: accepted (revised — the registry is a catalog owned by the domain modules, not a default layout).

The dashboard is composed of **Widget definitions declared in code** (each domain module exports the definitions it owns, and the dashboard's `registry.ts` aggregates them), not rows in a database-backed widget builder. The registry is a **catalog, not a default layout**: a user who has saved nothing sees an empty dashboard and adds widgets from the permission-filtered library. A user's layout is a JSON document stored per user in `DashboardLayout` — a list of instances keyed by a stable instance key.

**Ownership.** The dashboard is a *composition root*, not the owner of every widget. A widget that presents a domain's data (drafts, scheduled content, reviews, orders, failed runs) is owned by that domain module: the module exports its `WidgetDefinition`, its component, and the query behind it. The dashboard aggregates those definitions and adds the generic Trend. The shared contract (`WidgetDefinition`, `WidgetComponentProps`, `Metric`, the instance type) lives in `src/shared/dashboard/`, so a domain module depends on the contract — never on the dashboard, which imports the modules. The same rule governs the server-side **Metric registry**: each metric is owned by the module whose data it aggregates, and the dashboard's metric registry aggregates them.

Widget identity is therefore a code string (e.g. `trend`) with no foreign key in the database. This is deliberate. The alternative — a database-driven widget model where users compose arbitrary persisted widget rows, or a materialized per-user layout at account creation — was rejected because it duplicates the visual page builder (Puck) for a much smaller surface and makes the catalog hard to evolve. With a registry, adding a widget is one module change plus one aggregation entry; removing one removes it from the library and drops it from every user's effective layout with no migration; and availability emerges from the permissions each definition declares, so no per-role layout storage is needed.

A definition may also declare a **config schema**, resolved against the user's context (for the Trend, the metrics the user may read). The chosen config is stored per instance in the same per-user document, so a widget becomes configurable — and a new configurable widget appears — with no model change. Multiple instances of one definition are allowed, so two Trend widgets can chart different metrics.

The cost is that the database cannot enforce the set of valid widget ids, and the pure, tested layout function (filter the saved instances by permission, drop unknown or unpermitted ones) is the single place that defines what a user actually sees. If a future requirement demands arbitrary admin-authored widget types or per-role layouts in the database, a per-role default can be inserted as an additional layer above the catalog without changing the storage shape.
