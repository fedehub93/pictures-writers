# Media storage seam and pregenerated renditions

Status: accepted

All uploaded files go through a `StorageDriver` seam (put, get, delete, delete-prefix, url) with one driver per install chosen by configuration, so a Media row never stores a provider URL as truth: it stores a storage key plus a manifest of derived renditions, and every deliverable URL is a projection. Renditions are produced at upload time, never in a request path, and served straight from the provider's CDN through a custom `next/image` loader — when a rendition is missing the loader falls back to the original instead of hitting our server, so the VPS never pays image CPU on the hot path.

The constraint is a single 4-vCPU/8 GB VPS with no paid external services and ~700 images (~0.1 GB): the Next.js optimizer would resize on that box for every unique `src × width × quality` and cache up to half the free disk, which competes with Postgres and builds. UploadThing stays the only driver in v1 (its 2 GB free tier holds the library and its renditions several times over, and it already serves through a CDN), but it is not S3-compatible, so the seam is what keeps a future move to R2 or local disk a copy job rather than a rewrite of post, page, product, Puck, TipTap and email content.

**Considered options**
- Keep `next/image` on-the-fly (current): zero code, but the CPU cost and the disk cache land on the VPS, and there is no way to bound either per visit.
- Cloudflare Images Transformations (5,000 unique transformations/month free): removes the CPU, but requires moving the domain's nameservers to Cloudflare and hits a monthly ceiling a sellable CMS outgrows immediately.
- Renditions generated on first request: same hot-path CPU as today with extra complexity, so rejected.
- Store renditions as `MediaVariant` rows: queryable, but thousands of rows that are pure derivations of one file; the manifest JSON on the Media row plus deterministic keys gives garbage collection by prefix with none of the row noise.

**Consequences**
- The rendition ladder equals `images.deviceSizes`/`images.imageSizes`, and the loader rounds down to the nearest generated width; quality is baked into each rendition, so `images.qualities` collapses to the ladder's values.
- `/_next/image` disappears from the delivery path and `images.remotePatterns` becomes irrelevant, removing an SSRF surface.
- The 674 legacy images get metadata backfilled once (bytes, MIME, dimensions, checksum, blur placeholder) and their renditions generated by an off-peak bulk job; until then the loader serves their originals.
- Replacing a Media's file bumps a revision counter in its storage key, so no CDN cache can serve the previous file and no content reference has to change.
- Archiving is soft: a Media leaves the library but keeps being served and referenced; permanent deletion is manual and removes every object through the driver recorded on the row, because the previous `bulk_delete` left renditions orphaned in storage.
- Duplicate uploads are surfaced by checksum with an "use the existing one" choice, never deduplicated silently: two rows with the same bytes but different alt text or folder are legitimate.
- Non-image Media are stored and served untouched: no video poster extraction, which would mean ffmpeg in the container.

**Revision (2026-11) - delivery hop and per-row driver.** Delivery is an application route, `GET /media/<key>`, rather than a build-time rewrite. The route reads the row, streams a local object, or answers a cacheable `302` to the provider's CDN; a rewrite would bake a single provider into the build and could not answer per Media. For the same reason `Media.storageDriver` records the driver that wrote each row instead of a per-Installation switch: changing the active driver affects only new uploads, every existing file keeps resolving through the driver that wrote it, and a later move is row by row rather than a switch that darkens half the site. New rows store the relative `/media/<key>` address with the provider origin carried in the rendition manifest; the legacy `/assets/<key>` rewrite stays for URLs stored before that address existed.

**Revision (2026-11) - the local address is canonical.** The local driver composes `/media/<key>` through `mediaPath`, the same address `Media.url` stores and the delivery route serves. The configurable `MEDIA_STORAGE_LOCAL_PUBLIC_URL` prefix is removed rather than validated: any other value would produce addresses the route cannot serve, and a leftover value in an environment file has no effect.

**Revision (2026-11) - every Media type uses the application transport.** Documents, audio and video now upload through the same multipart endpoint as images, are written by the active driver under their own revision and record that driver on the row. They are stored untouched and have no renditions. Images keep the 4 MB limit and every other type gets 16 MB, matching the limits the library enforced while UploadThing owned the transport. A MIME type the classifier in `src/modules/media/lib/media-type.ts` cannot place is refused before any bytes are written; an oversize, quota-refused, unclassifiable or duplicate upload each answers a distinct machine-readable code, and a refused upload leaves no row and no object behind.

**Revision (2026-11) - the active driver is a setting.** The driver used by new uploads is chosen in the media library and stored on `Settings.storageDriver`. Resolution happens per request and reads the saved setting, then `MEDIA_STORAGE_DRIVER`, then the historical default, so an Installation that never touches the choice keeps writing where it does today and a switch takes effect on the next upload with no restart or redeploy. Delivery keeps resolving per row. `UPLOADTHING_TOKEN` stays in the environment until storage becomes an Integration, which narrows rather than ends ADR-0023's environment exception to the credential.

**Revision (2026-11) - deletion resolves the driver per row.** Permanent deletion resolves the driver recorded on each selected Media, so a library mixing legacy provider rows and rows written by another driver is cleaned on both sides in one batch. A namespaced Media is removed by its whole installation directory; a row with no recorded driver stores the provider's own file key, which a customId prefix scan cannot address, so that exact object is removed instead. A driver this build does not know, or one whose credentials are absent here, does not abort the batch: the rows are deleted and each object left behind is reported, because keeping a row whose bytes are already gone is worse than an object an operator can still see and clean up.
