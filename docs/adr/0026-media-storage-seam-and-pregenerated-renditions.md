# Media storage seam and pregenerated renditions

Status: accepted

All uploaded files go through a `StorageDriver` seam (put, delete, url, presigned upload) with one driver per install chosen by configuration, so a Media row never stores a provider URL as truth: it stores a storage key plus a manifest of derived renditions, and every deliverable URL is a projection. Renditions are produced at upload time, never in a request path, and served straight from the provider's CDN through a custom `next/image` loader — when a rendition is missing the loader falls back to the original instead of hitting our server, so the VPS never pays image CPU on the hot path.

The constraint is a single 4-vCPU/8 GB VPS with no paid external services and ~700 images (~0.1 GB): the Next.js optimizer would resize on that box for every unique `src × width × quality` and cache up to half the free disk, which competes with Postgres and builds. UploadThing stays the only driver in v1 (its 2 GB free tier holds the library and its renditions several times over, and it already serves through a CDN), but it is not S3-compatible, so the seam is what keeps a future move to R2 or local disk a copy job rather than a rewrite of post, page, product, Puck, TipTap and email content.

**Considered options**
- Keep `next/image` on-the-fly (current): zero code, but the CPU cost and the disk cache land on the VPS, and there is no way to bound either per visit.
- Cloudflare Images Transformations (5,000 unique transformations/month free): removes the CPU, but requires moving the domain's nameservers to Cloudflare and hits a monthly ceiling a sellable CMS outgrows immediately.
- Renditions generated on first request: same hot-path CPU as today with extra complexity, so rejected.
- Store renditions as `MediaVariant` rows: queryable, but thousands of rows that are pure derivations of one file; the manifest JSON on the Media row plus deterministic keys gives garbage collection by prefix with none of the row noise.

**Consequences**
- The rendition ladder equals `images.deviceSizes`/`images.imageSizes`, and the loader rounds down to the nearest generated width; quality is baked into each rendition, so `images.qualities` collapses to the ladder's values.
- `/_next/image` disappears from the delivery path and `images.remotePatterns` becomes irrelevant, removing an SSRF surface.
- The 674 legacy images get metadata backfilled once (bytes, MIME, dimensions, checksum, blur placeholder) and their renditions generated by an off-peak bulk job; until then the loader serves their originals.
- Replacing a Media's file bumps a revision counter in its storage key, so no CDN cache can serve the previous file and no content reference has to change.
- Archiving is soft: a Media leaves the library but keeps being served and referenced; permanent deletion is manual and removes the whole `<id>/` prefix (original plus renditions), because the previous `bulk_delete` left renditions orphaned in storage.
- Duplicate uploads are surfaced by checksum with an "use the existing one" choice, never deduplicated silently: two rows with the same bytes but different alt text or folder are legitimate.
- Non-image Media are stored and served untouched: no video poster extraction, which would mean ffmpeg in the container.
