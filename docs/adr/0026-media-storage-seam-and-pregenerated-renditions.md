# Media storage seam and pregenerated renditions

Status: accepted

All uploaded files go through a `StorageDriver` seam (put, get, delete, delete-prefix, url) with one driver per install chosen by configuration, so a Media row never stores a provider URL as truth: it stores a storage key plus a manifest of derived renditions, and every deliverable URL is a projection. Renditions are produced at upload time, never in a request path, and served straight from the provider's CDN through a custom `next/image` loader — when a rendition is missing the loader falls back to the original instead of hitting our server, so the VPS never pays image CPU on the hot path.

The constraint is a single 4-vCPU/8 GB VPS with no paid external services and ~700 images (~0.1 GB): the Next.js optimizer would resize on that box for every unique `src × width × quality` and cache up to half the free disk, which competes with Postgres and builds. UploadThing stays the only driver in v1 (its 2 GB free tier holds the library and its renditions several times over, and it already serves through a CDN), but it is not S3-compatible, so the seam is what keeps a future move to R2 or local disk a copy job rather than a rewrite of post, page, product, Puck, TipTap and email content.

**Considered options**
- Keep `next/image` on-the-fly (current): zero code, but the CPU cost and the disk cache land on the VPS, and there is no way to bound either per visit.
- Cloudflare Images Transformations (5,000 unique transformations/month free): removes the CPU, but requires moving the domain's nameservers to Cloudflare and hits a monthly ceiling a sellable CMS outgrows immediately.
- Renditions generated on first request: same hot-path CPU as today with extra complexity, so rejected.
- Store renditions as `MediaVariant` rows: queryable, but thousands of rows that are pure derivations of one file; the manifest JSON on the Media row plus deterministic keys gives garbage collection by prefix with none of the row noise.

**Consequences**
- The rendition ladder equals `images.deviceSizes`/`images.imageSizes`, and the loader rounds down to the nearest generated width; quality is baked into each rendition, so `images.qualities` collapses to the ladder's values.
- `/_next/image` disappears from the delivery path and `images.remotePatterns` becomes irrelevant, removing an SSRF surface.
- The 674 legacy images get metadata backfilled once (bytes, MIME, dimensions, checksum, blur placeholder) and their renditions generated by an off-peak bulk job; until then the loader serves their originals.
- Replacing a Media's file bumps a revision counter in its storage key, so no CDN cache can serve the previous file and no content reference has to change.
- Archiving is soft: a Media leaves the library but keeps being served and referenced; permanent deletion is manual and removes every object through the driver recorded on the row, because the previous `bulk_delete` left renditions orphaned in storage.
- Duplicate uploads are surfaced by checksum with an "use the existing one" choice, never deduplicated silently: two rows with the same bytes but different alt text or folder are legitimate.
- Non-image Media are stored and served untouched: no video poster extraction, which would mean ffmpeg in the container.

**Revision (2026-11) - delivery hop and per-row driver.** Delivery is an application route, `GET /media/<key>`, rather than a build-time rewrite. The route reads the row, streams a local object, or answers a cacheable `302` to the provider's CDN; a rewrite would bake a single provider into the build and could not answer per Media. For the same reason `Media.storageDriver` records the driver that wrote each row instead of a per-Installation switch: changing the active driver affects only new uploads, every existing file keeps resolving through the driver that wrote it, and a later move is row by row rather than a switch that darkens half the site. New rows store the relative `/media/<key>` address with the provider origin carried in the rendition manifest; the legacy `/assets/<key>` rewrite stays for URLs stored before that address existed.

**Revision (2026-11) - the local address is canonical.** The local driver composes `/media/<key>` through `mediaPath`, the same address `Media.url` stores and the delivery route serves. The configurable `MEDIA_STORAGE_LOCAL_PUBLIC_URL` prefix is removed rather than validated: any other value would produce addresses the route cannot serve, and a leftover value in an environment file has no effect.

**Revision (2026-11) - every Media type uses the application transport.** Documents, audio and video now upload through the same multipart endpoint as images, are written by the active driver under their own revision and record that driver on the row. They are stored untouched and have no renditions. Images keep the 4 MB limit and every other type gets 16 MB, matching the limits the library enforced while UploadThing owned the transport. A MIME type the classifier in `src/modules/media/lib/media-type.ts` cannot place is refused before any bytes are written; an oversize, quota-refused, unclassifiable or duplicate upload each answers a distinct machine-readable code, and a refused upload leaves no row and no object behind.

**Revision (2026-11) - the active driver is a setting.** The driver used by new uploads is chosen in the media library and stored on `Settings.storageDriver`. Resolution happens per request and reads the saved setting, then `MEDIA_STORAGE_DRIVER`, then the historical default, so an Installation that never touches the choice keeps writing where it does today and a switch takes effect on the next upload with no restart or redeploy. Delivery keeps resolving per row. `UPLOADTHING_TOKEN` stays in the environment until storage becomes an Integration, which narrows rather than ends ADR-0023's environment exception to the credential.

**Revision (2026-11) - deletion resolves the driver per row.** Permanent deletion resolves the driver recorded on each selected Media, so a library mixing legacy provider rows and rows written by another driver is cleaned on both sides in one batch. A namespaced Media is removed by its whole installation directory; a row with no recorded driver stores the provider's own file key, which a customId prefix scan cannot address, so that exact object is removed instead. A driver this build does not know, or one whose credentials are absent here, does not abort the batch: the rows are deleted and each object left behind is reported, because keeping a row whose bytes are already gone is worse than an object an operator can still see and clean up.

**Revision (2026-11) - the mixed library is the accepted end state.** Existing Media are not migrated: the pre-seam rows keep their absolute UploadThing addresses and their missing driver record, new uploads may go to local disk, and both keep serving. Switching the active driver is therefore not a migration event - it changes where the next upload is written, while delivery, replacement, deletion and both backfills resolve the driver recorded on each row. The `302` hop serves any row whose recorded driver is not local, including a pre-seam row with no record; that row stores an absolute address, so the browser asks the provider directly and does not request the route. The hop is therefore not a path to own-domain addresses for legacy Media; routing them through it would add a provider lookup or a rewrite to every existing image. `npm run media:audit` is the read-only proof of the mixed state: rows per driver, unresolved Media ids, local bytes against accounted bytes, and a non-zero exit when anything is unresolved.

**Revision (2026-11) - delivery reads the stored-file record.** The route resolves the location record by key rather than the Media's storage columns. A local file streams with the content type, ETag, byte length and Range support the record and disk provide; a remote file is a `302` to the address the record carries, with `Cache-Control: public, max-age=300` and never `immutable`, because the hop points at bytes a later move can take away. The hop performs no provider API call. A rendition has no record of its own: it resolves through its Media's revision prefix and, when the Media is remote, its provider address comes from the rendition manifest. A Media whose record has not been created yet still resolves from its own columns, so deploying this code before the one-time backfill cannot darken an existing picture.

**Revision (2026-11) - writes read the stored-file record.** Replacement and permanent deletion resolve the key and driver from the file's record, and the key's shape decides the unit of cleanup: a namespaced key is removed by prefix, while a recorded provider address with a key outside that grammar is the provider's own file key and is removed exactly, which is what a backfilled pre-seam row now is. A driver that is not configured, or a cleanup that fails, never fails a replace and is reported as its outcome; deletion still resolves each selected file separately and never one driver for a whole batch. The admin library reads the record's key, size, content type, checksum and driver, while `Media.url` remains the canonical address composed from the key. The Media's storage columns are written in step and read only for a row whose record does not exist yet, until the contract change removes them.

**Revision (2026-11) - attachments and avatars are roles on the same record.** An email or form attachment and a user avatar are `StoredFile` rows of another kind, not provider URLs of their own. They are written through the same application transports as library uploads, answer under `/files/<key>` with the same content type, cache and Range behaviour as a local Media, and never acquire a Media, a rendition or a library row. The canonical address is composed by the same function that composes `/media/<key>`; only the prefix distinguishes the role. An attachment is owned by exactly one message or form submission and an avatar by one user, so deleting the owner removes the objects through the driver recorded on each file. A driver that is not configured here is reported by the audit and its record is kept, because losing the location of bytes is worse than leaving an object an operator can still clean up. Inbound email takes the same route: the webhook handler downloads the provider's expiring attachment URL and writes it through the active driver before recording the message, so the provider's copy is never the only one; a storage failure is logged per attachment and the message still arrives without that file. The skip is final: the recorded message id makes a provider retry a no-op, so an attachment lost to a transient storage failure is not fetched again.

**Revision (2026-11) - public form attachments are anonymous and budgeted.** A form submitter is not an admin, so the public attachment transport (`POST /api/forms/<formId>/attachments`) is unauthenticated by design. It is bounded twice: a 4 MB per-file cap, and two in-memory windows, one per client and one per form (30 uploads a minute for the form, 10 for the client). The form window is spent only by a real file for a real form, so an empty POST cannot deny uploads to its visitors; a refused request leaves no bytes and no record. Every file it writes is `origin = public`, which is what lets the quota reserve protect the owner's library from strangers; the reserve itself is a later decision. The upload answers with the stored-file id and the canonical `/files/<key>` address, and the submission claims that id in the same transaction that saves the answer. The answer's address is recomposed from the claimed record rather than trusted from the browser, so no submission can carry a provider address, even if the visitor crafts the request. The designer renders the upload control disabled because it has no form to upload to, and the public transport is the only path a visitor's file takes.

**Revision (2026-11) - one quota over every file, with a reserve for public origin.** The budget is no longer media-only: every `StoredFile` counts, so the library's single number describes the disk. A Media contributes its original's stored-file size plus its rendition manifest, an attachment or avatar its own bytes, archived Media keep counting, and a Media whose location record the one-time backfill has not created yet still counts from its own columns. `Settings.publicOriginReserveMb` (default 512 MB, a tenth of the default 5 GB quota) is the share public-origin files may occupy inside that number. A public upload must fit both the total and the reserve; an internal upload is bounded by the total only. Every transport — library, admin attachment, avatar and public form — takes the same advisory lock at admission, so a public refusal and an admin upload started at the same moment never block each other. A refusal carries a machine-readable code (`MEDIA_QUOTA_EXCEEDED` for the total, `PUBLIC_ORIGIN_RESERVE_EXCEEDED` for the reserve) and leaves no bytes and no record. Zero refuses every public upload, an Installation with no public forms never reaches the reserve, and nothing is deleted automatically for budget reasons: permanent deletion and deleting an attachment's or avatar's owner are what free the bytes.

**Revision (2026-11) - no provider code in a user path.** The browser no longer ships the provider's client library: the provider file router and its public route are gone, along with the three endpoints that had no caller (the legacy media upload, the post image and the impression file) and the JSON branch of `POST /api/media`. Every upload the product offers - the library, email attachments and avatars, public form attachments, inbound email copies - reaches storage through an application transport and the active driver, so an Installation with no token has no provider code on any path a visitor, an admin or a form submitter can take. The provider survives only as a server-side driver, built from `UPLOADTHING_TOKEN` in a module marked `server-only`. Removing the browser path does not remove the provider's host grammar: an address stored before the canonical form still has to be recognised so the address sweep can report or rewrite it rather than tolerate it silently.

**Revision (2026-11) - the fallback driver is local.** An Installation with no saved choice and no `MEDIA_STORAGE_DRIVER` now writes new uploads to local disk instead of the provider, because a fresh Installation must upload with no provider account. An Installation already on a provider records `uploadthing` explicitly before adopting this code, so the change of fallback cannot move its next upload; the human deploy step owns that record.

**Revision (2026-11) - re-home moves bytes, never an address.** Moving the library to the active driver is a separate, explicit job, not a consequence of the switch. It recomputes its goal from the database at every start - every `StoredFile` on the active driver - and copies one file at a time, a Media's original and its rendition manifest included. The source is verified against the checksum the record carries and the copy is read back from the target before anything changes; then one transaction flips the record's `driver` and `remoteUrl` and rewrites the Media's `?mt=` token with the new rendition addresses. The key, the revision and the original's canonical address never change, so a run can last hours, be interrupted, be stopped and be resumed without a visitor seeing a different address. A failure before the flip removes the target copy and leaves the source serving, which is why no failure can break an address. A Media still addressed by a provider URL is refused (`address-not-canonical`) until the address sweep has rewritten it, because journaling that object would let the purge remove bytes published pages still link to. A newer driver choice supersedes the run at the next file and the next run converges. A local target's preflight reserves 10% headroom over the bytes it copies: the copies fitting but not the headroom needs confirmation, the copies not fitting is refused, and a file whose recorded size is unknown also needs confirmation because the estimate cannot describe it. Every provider object the move abandons is recorded in `StoragePurgeEntry` by driver and exact key, because a pre-seam key is not namespaced and a prefix scan cannot find it; a key that becomes live again on a driver has its journal entry removed in the same flip, and the journal is what the separate purge command acts on after its grace window. A local source is deleted after the flip instead, since there is no cache hop to wait out. The mixed library is therefore a transition between two drivers, not the target, and `npm run media:audit` proves each hop.

**Revision (2026-11) - the address sweep rewrites the strings, not the bytes.** A library that predates the seam keeps the provider's absolute URL in `Media.url` and in every content string that copied it. `npm run media:sweep-addresses` builds one index from the Stored files - a Media's `/media/<key>`, an attachment's or avatar's `/files/<key>` - and rewrites each provider URL, legacy `/assets/` shape and an absolute address the library already recorded into the canonical address of the file it names; an ordinary external link is left alone. A content address names each rendition by its own `/media/<key>` path, so a later move cannot leave a provider URL inside a page, while the `Media.url` row keeps the rendition token it already carries, because that token is what lets the delivery route redirect a remote rendition before the bytes move. An address no Stored file owns is reported by field and count, never by address, and fails the command. The run writes no Stored file: keys, revisions, drivers and remote locations are read, never changed. It is idempotent, offers a dry run, and has to precede a Re-home, because a Media still addressed by a provider URL is refused by the move.
