# Render email bodies in a sandboxed iframe

**Status**: accepted

The Conversations mailbox used to show every message as plain text. The thread preferred the stored text part and otherwise stripped the HTML, and the Inbox and Sent previews inherited the same lossy text, because the earlier decision was that "the inbox never renders email HTML": a stored body is untrusted input and must not reach the app origin. That stance was recorded in the inbox ticket of the email-conversations spec rather than in an ADR; this decision supersedes it. It kept the admin safe but lost bold, italics, lists, links, alignment and paragraph spacing in both Sent and Received, and the editor's plain-text extraction could turn a list after a paragraph into a blank gap.

We now render the stored HTML of each message in an `iframe` whose document is supplied through `srcdoc`, with `sandbox="allow-scripts"` and deliberately without `allow-same-origin`, `allow-forms`, `allow-top-navigation` or `allow-popups`. The frame has no access to the application origin, and the document carries its own restrictive CSP. The body is still treated as hostile: the builder strips `script`, `iframe`, `object`, `embed`, `form`, `input`, `link` and `meta` elements, every `on*` attribute and `javascript:`, `vbscript:` and `data:text/html` URLs, and remote references are removed unless the user reveals them. The reversal is about who provides the isolation boundary, not about trusting the body: a browser sandbox replaces a text-only compromise.

The iframe is chosen because a body can come from any sender and any past composer, and no transformation we run on the app origin gives the same guarantee. The browser enforces the frame as an opaque origin, so a markup or sanitizer mistake cannot read app state, cookies or the DOM. The document's CSP pins the only script that may run — the height/link reporter — by SHA-256, and a test recomputes that hash so the CSP cannot silently drift. An inline script in the stored body has no matching hash and does not execute, and stored `script` elements are removed before the document is built.

## Considered options
- **Keep plain text only**: cheapest and already in place, but it silently destroys the formatting the CMS composes and sends, and the derived text part is itself lossy. Rejected: the mailbox has to show what the recipient received.
- **Sanitize the HTML and inject it into the app DOM**: DOMPurify or an equivalent removes dangerous markup, but it runs in the app origin, so a bypass or a future configuration mistake is a direct XSS against the admin, and email HTML relies on constructs sanitizers tend to strip. Rejected as the primary boundary.
- **Sandboxed iframe (chosen)**: the browser is the isolation boundary and needs no parser of our own; the cost is a fixed document, a pinned script and `postMessage` plumbing for height and links.

## Consequences
- Scripts are limited to the one hash-pinned height/link reporter. Every other inline script is blocked by the CSP, and every stored `script`, `iframe`, `object` and `embed` element is stripped. `allow-scripts` is required for the reporter but comes without `allow-same-origin`, so the script cannot touch the parent document.
- Links do not navigate the frame: the reporter intercepts `http`, `https` and `mailto` clicks and the parent opens them in a new tab with `noopener,noreferrer`. The parent accepts height and link messages only from the frame's `contentWindow`; `event.origin` is `"null"` for an opaque origin and is never trusted.
- Remote content is blocked by default. Remote `src`, `srcset`, `poster`, `background` and CSS `url()` references are removed while blocked, so the browser shows no broken-image placeholders, and the builder reports whether any remote content existed. A per-message "Show images" control appears only when it can do something, rebuilds the document with the references restored, and resets on unmount; nothing is persisted.
- Email styling never leaks into the app and app styling never leaks in. The frame uses a fixed white background, a neutral sans-serif stack at 14px with 1.6 line height, `max-width: 100%` for images and tables, and word wrapping. It does not follow the admin's light or dark theme, so sender colours stay readable but the message never matches the surrounding theme.
- Height is automatic and uncapped: the frame reports its content height on `ResizeObserver`, on load and after images finish loading, and the parent applies it. The thread remains the only scroll container, so there is no nested scrollbar and a resize never forces the thread to scroll.
- `cid:` inline images remain unresolved. A received message that references an embedded `Content-ID` image still points at a `cid:` URL the frame cannot load, because attachments do not store the `Content-ID`. This is accepted for now and handled by a separate ticket; it is not a reason to run remote content or scripts.
- No schema or migration change is needed: `EmailMessage.bodyHtml` and `bodyText` already exist, so historical outbound messages, which already carry HTML, become correct as soon as the rendering lands. Messages without HTML keep the text fallback, and collapsed messages render no frame.
