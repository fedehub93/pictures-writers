# Site regions as first-class versioned entities

**Status**: accepted

The public header and footer were hard-coded React components. To let each Installation compose them in Puck, they need stored content with the same safety properties as a page: an unpublished revision the editor can iterate on, a published revision the public site renders, history, unpublish, and a change that reaches every page at once. We therefore store each one as a dedicated `SiteRegion` root plus `SiteRegionVersion` revisions, keyed by the `SiteRegionKey` enum (`HEADER`, `FOOTER`), and reuse the Root + Version contract established for `Page` (ADR-0011). `currentVersionId` points at the revision the editor is working on and `liveVersionId` at the revision the public layout renders; editing the live revision forks a `CHANGED` revision, publishing locks the root row, promotes the target and demotes the previous live version, and unpublishing clears the live pointer and returns the revision to `CHANGED`. `firstPublishedAt` lives on the root and is written only once. The key is unique because an Installation has at most one header and one footer; roots are created lazily, so a region can be absent until its editor is first opened. Because each Installation owns its database (ADR-0036), that uniqueness needs no tenant column.

The public layout reads only the live version through `getCachedLiveRegionByKey`. When there is no live version — the root was never created, was never published, or was unpublished — the layout renders a **generic default** from `lib/default-regions.ts`: a `Brand`-only header and a `Copyright`-only footer, so a fresh Installation never inherits Pictures Writers branding. The default is code, not seeded rows, and a persisted region starts empty. A *published empty document* is respected as a deliberate headerless or footerless site; only a null document triggers the fallback.

Permissions are a separate `site_layout` area (`read`, `update`, `publish`), not part of `pages`. Editing the global layout has a larger blast radius than editing a page, and the split lets a Tenant grant page access without granting layout access. `ADMIN` and `EDITOR` receive all three actions in the initial seed, and the admin menu gates the new area on `site_layout.read`. Creating a root happens on the first editor open, so it resolves to `site_layout.update` rather than a `create` action.

A region renders in the layout of every page, so publishing or unpublishing calls `revalidatePath("/", "layout")` and `revalidateTag` on the region cache tag. The public layout resolves both regions through `unstable_cache` with a 60-second time-to-live; the TTL is only a backstop, on top of the same on-demand revalidation strategy as the rest of the site (ADR-0001).

## Considered options

- **Special `Page` rows with reserved slugs** (for example `__header__`). It would reuse the existing editor, versioning and publish flow. Rejected: those rows would surface in the page list, slug uniqueness, sitemap, search and generic page queries, so every consumer would need to exclude them; they compete for the public slug namespace; they are indistinguishable from real pages in the admin UI and easy to edit or delete; and the `pages` permission would implicitly grant control of the global layout. Their URL semantics are wrong too: a header is not a routable page.
- **Extend the `Widget` table**. The `Widget` model is the public site-widget builder — rows typed by `WidgetSection` (`HERO`, `MODAL_POPUP`, `POST_SIDEBAR`, `POST_BOTTOM`) with `isEnabled`, `sort` and `metadata` (the dashboard's code-defined registry in ADR-0015 is a different mechanism). Rejected: `Widget` is not versioned and has no Puck document, `currentVersionId` or `liveVersionId`; a section holds many rows ordered by `sort`, while a Site region is one root per key. Adding the region lifecycle there would either version every site widget or leave a table where most columns apply to two rows only, and it would mix two publication models in one entity.
- **Store the regions as JSON in `Settings`**. Cheapest schema change, but it has no revisions, no publish/unpublish, no row lock and no history, so concurrent saves overwrite each other and a bad edit is immediately global and unrecoverable. It also couples public layout content to the settings permission and its update path.
- **Dedicated `SiteRegion` root + versions keyed by an enum** (chosen). It gives the region the same versioning, locking and publication semantics as a page while keeping the identity set closed (a new region is a migration, not a free-form slug), and it isolates the permissions, the admin screens and the revalidation from pages and widgets. The cost is a new table pair, its own save/publish plumbing, and a migration whenever a future region key is added. Sharing `Page`'s helpers was not worth it: they are bound to slug, SEO and scheduling, none of which a region has, so a shared function would either parameterise those concerns or become a thin wrapper over two different lifecycles.

## Consequences

- Each new region key requires a Prisma enum migration. The closed set is intentional: regions are part of the application contract, unlike pages, whose slugs are content.
- The public layout resolves both regions through one cached read per region (`unstable_cache`, 60-second TTL); publish and unpublish invalidate the cache tag and the layout path, so the change is visible without a deploy.
- The editor uses a per-region Puck palette, so header-only blocks such as `NavbarBlock` cannot be dropped into the footer and vice versa.
- The admin screen lists one entry per region key, including keys whose root has not been created yet, with the current and live status. Version history is kept per root and exposed by `getVersions`; it has no dedicated screen in this iteration.
- The static `Navbar` and `Footer` components remain in source but are no longer imported by the public layout. Removing them is a later cut-over after Pictures Writers has recreated its layout with Site regions; it is not part of this decision.
- The canonical terminology and boundaries are recorded in `CONTEXT.md` "Site layout"; the full feature scope is in `.scratch/site-regions/spec.md`.
